# FW_Test — 本体ファームウェア変更の確認ソフト

本体ファームウェアに入れた次の変更が、正しく動いているか・速くなったかを実機で確かめる Lua ソフトです。

| 番号 | 変更 | ファイル |
|------|------|----------|
| 1 | LCD 転送: 帯バッファを SPI 16bit で 1 回の DMA で直接送る（CPU が描画中でも転送が止まらない。バイト並べ替え不要） | `lib/ST7789/st7789_lcd.cpp/.hpp` |
| 2 | フレーム末の LCD 転送完了待ちを廃止（最後の帯の転送を次フレームの処理と重ねる） | `lib/lua_interpreter/lua_interpreter.cpp` |
| 6 | 変化した帯の判定（帯ハッシュ）を 12 回走査 → 1 回走査に | `lib/lua_interpreter/draw_command_list.cpp/.hpp` |
| 7 | BGM の SD 読み込みを最大 64 サンプルずつまとめる・再生位置計算を整数化 | `lib/lua_interpreter/lua_audio.cpp/.hpp` |
| BGM 修正 | 下の「BGM の不具合修正」を参照 | `lua_audio.cpp/.hpp`・`lua_interpreter.cpp` |

Lua API はどれも変えていないので、既存ゲームはそのまま動きます。
静的 RAM 使用量は変更前と同じ（123,448 バイト）です。

## BGM の不具合修正（すべて Lua からの使い方は変わりません）

| 不具合（変更前） | 修正後 |
|------------------|--------|
| 44.1kHz 以外の WAV の再生で線形補間が効かず（前の値の引き延ばし）、1 サンプル遅れていた | 正しく線形補間（理想値との差 1 LSB 以内） |
| 44.1kHz 以外の WAV は最後まで再生しても止まらず、最後の値を出し続けていた（処理も回り続けた） | 44.1kHz と同じくファイル末尾で停止 |
| 2 つあるストリームバッファを「読める方から」使っていたため、補充のタイミングによっては新しい音が古い音より先に鳴っていた（プツプツ音の原因） | 書いた順に読む（FIFO） |
| BGM の補充がフレーム先頭の 1 回だけで、先読みは約 11.6ms 分しかないため、30FPS 前後では補充が追いつかず途切れていた | 描画前と、LCD へ送る帯ごとにも補充 |

## SD への配置

ゲーム選択メニューは SD の `/games` しか見ないので、このフォルダを **`/games/FW_Test/`** としてコピーしてください。

```
/games/FW_Test/
├── FW_Test.lua
├── fonts/game_font.bin
├── img/test16.bin
└── audio/*.wav   （テスト用 WAV 14 個）
```

`audio/`・`img/`・`fonts/` は `generate_test_assets.py` で作り直せます（numpy・Pillow が必要）。

## 手順（旧ファームと新ファームの比較）

1. **旧ファーム**を書き込み、「6 自動ベンチマーク」を実行（約 70 秒。放置で OK）
2. **新ファーム**を書き込み、もう一度「6 自動ベンチマーク」を実行
3. 「7 結果比較」を開く → 前回＝旧、今回＝新 の FPS が並びます
4. 新ファームで下の目視・耳のテストを行う

## 各テストの見方

| テスト | 確認すること | 合格の目安 |
|--------|--------------|------------|
| 0 色・表示チェック | 色見本 8 色・階調・テスト画像（変更 1 のバイト順） | 名前どおりの色、左→右に明るくなる |
| 1 描画スイープ | 11 種類の描画命令が 12 本の帯をまたいで動く | 残像・欠け・ちらつきが無い（OP-R の clear モードでも） |
| 2 帯スキップ FPS | 変化する帯 0／1／6／12 本の FPS | 変化が少ないほど高い。「全12帯変化」は変更 1・2 で上がる |
| 3 命令多め・変化小 | 静止矩形 300／600／900 個＋1 帯だけ変化 | 変更 6 で上がる |
| 4 BGM 形式テスト | 44.1k／22.05k／11.025k／48k／32k／8k、モノ・ステレオ、壊れ気味のファイル | 0〜1 秒は左、1〜2 秒は右から 440Hz。クリックが右上の点滅と合う。音の高さが全部同じでプツプツしない |
| 5 BGM 負荷測定 | 静止画面で BGM なし／ありの FPS | 「負荷%」が旧より小さい |
| BGM 途切れテスト | 重い描画（全帯変化）をしながら 44.1k の BGM | 途切れ・プツプツが無い |
| エラー表示テスト | 描画転送中に本体のエラー表示（LCD 直接描画）が走る | 乱れずに「Game start failed」画面が出て、メニューに戻れる |

## シリアルでの自己照合（任意）

`lib/lua_interpreter/draw_command_list.cpp` 先頭の `DRAW_CMD_HASH_SELFTEST` を `1` にしてビルドすると、毎フレーム新旧 2 つの方法で帯ハッシュを計算して照合し、USB シリアルに出力します。

```
[HASH-SELFTEST] 300 frames: mismatch=0  new=xx us/f  old=yy us/f
```

検証が終わったら `0` に戻してください。

## PC 上で行った検証

- **帯ハッシュ（変更 6）**: ランダムな描画命令 約 400 万個で、新旧の結果が全帯で完全一致
- **BGM（変更 7・修正）**: `lua_audio.cpp` を PC でそのまま動かし、30 種類の WAV で確認
  - 44.1kHz: 出力は元データと完全一致
  - 44.1kHz 以外: 理想的な線形補間との差が 1 LSB 以内
  - 全形式でファイル末尾で停止
  - 補充の間隔を変えても（毎回／2 回に 1 回）順序が崩れない（変更前は崩れていた）
  - `f_read` 呼び出し回数: ステレオ 1/32、モノラル 1/64
- **LCD 転送（変更 1・2）**: SPI・DMA・GPIO と ST7789 の受信動作をまねるモックの上で、実際の `st7789_lcd.cpp` と `game_display.cpp` を動かして確認（400 フレーム）
  - 対象: ランダムな帯更新、LCD への直接描画、全画面転送、行の途中で折り返す転送（従来経路）
  - 結果: LCD に届いた画像が期待どおり、SPI の規約違反もなし（DMA 中の書き込み・形式変更・CS 解放など）
  - 比較: 変更前のコードでフレーム末の待ちを外すと、規約違反が 3,571 回出る（コマンド送信前の完了待ちが必要な理由）
- **RP2350 向けビルド**（pico-sdk 2.2.0）が通ること、静的 RAM が変わらないことを確認
